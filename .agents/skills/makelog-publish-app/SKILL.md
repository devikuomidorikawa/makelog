# MAKELOGへアプリを掲載する

対象はユーザーが所有・制作するアプリ。MAKELOGの公開元は `devikuomidorikawa/makelog`、公開URLは https://devikuomidorikawa.github.io/makelog/ 。指定された別リポジトリへ勝手に転用しない。

## 最初に把握すること

依頼中のアプリと、ユーザーが渡したコード・仕様・画像・URL・現在の会話を読む。別のChatGPT会話、未添付ファイル、アカウント内の全アプリを自動取得できると推測しない。必要ならアクセス可能な接続を確認し、なければアプリのURL・コード・機能説明など不足する根拠だけを求める。決まっている配色・言語・掲載先・無料方針を聞き直さない。

「紹介案を作る」「準備する」なら掲載案と編集差分まで。「MAKELOGへ掲載・公開して」と依頼されていれば、必要な検証と公開確認まで進む。スキルの呼出しだけを、アプリのソース全公開・外部デモ公開・新しい権限付与・課金の許可にしない。制作途中のアプリは、その段階と試せる範囲を明記する。

## 読者に伝わる紹介を作る

- 一覧用には、作品名と「誰の・どんな困りごとを・どう解くか」が伝わる短い紹介を作る。技術名だけで価値を説明しない。既存の行一覧に収まる分量にし、長い宣伝文を重ねない。
- 詳細は、課題、実際にできること、主な設計判断、確認できる結果を具体的に書く。コードや実演で確認できた実装と、構想・未実装・未検証を区別する。架空の利用者数、成果数値、AI推論、連携、性能、安全性を実績として作らない。
- 日英を対応させる。日本語を主体にし、英語も同じ範囲・同じ確度で書く。既存の固有名・タグ・記事IDを維持する。
- 制作ノートはユーザーが求めた場合、または設計判断を残すことが掲載目的に必要な場合に追加する。単なる説明の重複のために記事を増やさない。
- 画像は実際の画面を優先し、公開可能なダミーデータで撮る。個人情報、APIキー、利用者の入力、私用のファイル名を含めない。非公開情報入りの原画像は下書きでもGitへ入れない。画面がなければ既存の線画アイコンによる紹介で始め、架空の動作画面を実物として見せない。

## MAKELOGへ組み込む

最新版の `main` と `AGENTS.md`、`AI-EDITING.md`、`SECURITY.md`、内容モデル、`.pages.yml` を読み、元コミットを記録する。実際のスキーマが以下と異なる場合は最新版を優先する。

- 既存作品は同じIDの項目を更新する。名称・GitHubリポジトリ・既存記事との対応で重複掲載を確認する。
- 新しいアプリは `src/content/site.json` の `site.additionalProjects` へ追加する。半角小文字英数字・ハイフンの固定IDを使い、既存の3サンプルを別アプリで上書きしない。掲載例と項目は [references/listing.md](references/listing.md) を読む。
- `updatedAt` は掲載内容の更新日（YYYY-MM-DD）。新規掲載と実質的な内容変更時に、ユーザー指定日または現在の日本時間の日付を設定する。アプリ自体の開発日と混同せず、無関係な作品の日付を更新しない。ホームは公開作品を日付の新しい順で3件自動表示するので、表示順を手動で書き換えない。
- タグは `src/content/tags/*.json` の既存表示名から選び、固定UUIDを参照する。足りない分類だけ新規追加する。既存タグのID、ファイル名、互換IDを変えず、改名・統合はタグ辞書で行う。
- デモURLや公開GitHubがないアプリも、紹介だけで掲載できる。URLを捏造せず、外部デモは実際にアクセスでき、ユーザーが公開を認めたHTTPSのものだけ設定する。ローカルURLを公開デモとして設定しない。アプリ本体を無料の静的サイトで動かせるとは限らない。API鍵・課金・サーバーが必要な処理を、掲載だけのために新設しない。
- 新しいデモの制作まで依頼された場合は通常の設計・開発・安全確認を行う。CLIなどをブラウザー用に移植した場合は「公開用の体験デモ」と明記し、元アプリとの違いを説明する。掲載だけの依頼から新規アプリ開発を始めない。
- 文章・画像・タグ・リンクの最小差分を作る。淡いベージュ、深紫、罫線、線画アイコン、既存のナビゲーションと余白を維持する。掲載依頼だけでサイトを作り直さない。

公開リポジトリの元ファイルとGit履歴は、`draft` も含めて閲覧可能。非公開コード・顧客情報・未発表実績は正本にも入れず、掲載用に一般化した説明やダミーへ置き換える。公開範囲が不明な実情報だけ確認し、独立して書ける紹介案は進める。

## 確認・公開・引き渡し

リポジトリ指定の内容検査、テスト、公開ビルド、静的ページ検査を行う。新しい入力・外部リンク・素材は既存の許可リストと検証を保ち、差分に見合う安全確認をする。重大な新しい処理がない文章更新に重い全体スキャンを機械的に繰り返さない。追加費用上限0円、Codex Security Cloudは使わない。通常のCodex利用枠は消費する。

PCとスマホで、ホームの上位3件、作品一覧、詳細、タグ、パンくず、日英、実在するデモ・GitHubリンクを確認する。記事を追加したら本文と関連作品への移動も確認する。指定のないデータや他の作品を変えていないことを差分で確認する。

公開を依頼されている場合は、反映直前の `main` と競合を確認してブランチ・PR経由で反映し、公開処理の成功後に実際の公開URLを開く。保存・PR作成・検査成功だけを公開完了と呼ばない。保存・公開権限がなければ、確認済みの掲載案と最小差分を渡し、未実施の操作を明示する。

最後は、作品URL、何を掲載・更新したか、実際に試せる範囲、確認結果、残る利用者の操作だけを簡潔に伝える。紹介文やデータを公開していない場合は、その状態を明記する。
